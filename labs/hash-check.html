Hash Check

Session 6 says a hash tells you whether a file changed. This lab makes you prove it: hash a file, change one character, hash it again, and then verify a real download against the hash its publisher posted. It's the same check a Bastion analyst runs before trusting a tool, and before handing a piece of evidence to anyone else.

Side project Builds on Session 6 · Module 10.1 Time ~30 min Difficulty Beginner

Objectives

What you'll do

  • Compute a SHA-256 hash from the command line on Windows, Linux, or macOS
  • Show that a one-character change produces a completely different hash
  • Show what a hash does not depend on (the file's name and location)
  • Verify a real download against its publisher's posted hash

Required resources

  • Any computer: Windows (PowerShell), Linux, or macOS (Terminal)
  • A plain text editor (Notepad, TextEdit in plain-text mode, nano, etc.)
  • An internet connection for Part 4
PlatformCommand to hash a file with SHA-256
Windows (PowerShell)Get-FileHash .\notes.txt (SHA-256 is the default)
Linuxsha256sum notes.txt
macOSshasum -a 256 notes.txt

Part 1

Hash a file you made

Start with a file whose contents you know exactly.

  1. Make a new folder called hashlab somewhere easy to find, like your Desktop or Documents.
  2. In a text editor, create a file named notes.txt in that folder containing exactly one line: Watch log: all quiet at gate 7. Save it.
  3. Open PowerShell or a terminal, change into the folder (cd), and run the hash command for your platform from the table above.
  4. Run the same command a second time. Compare the two results character by character.

Part 2

Change one character

Now see the avalanche effect for yourself.

  1. Open notes.txt and change 7 to 1. Change nothing else. Save it.
  2. Hash it again and fill in the table.
  3. Change it back to 7, save, and hash once more.

Here's the same effect on three tiny inputs, computed with SHA-256. Notice the third one: the only difference from the first is an invisible newline at the end.

"hello"    2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
"Hello"    185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
"hello\n"  5891b5b522d5df086d0ff0b110fbd9d21bb4fc7163af34d08286a2e846f6be03
Why your hash won't match a classmate's: if someone pressed Enter after the line, or their editor saved Windows-style line endings or a byte-order mark, their file contains different bytes even though it looks identical. The hash is computed on bytes, not on what you see on screen. Compare with a classmate and see whether yours match.

Part 3

What doesn't change the hash

A hash covers a file's contents. Find out what else it ignores.

  1. Copy notes.txt to a new file named evidence-copy.txt (in File Explorer/Finder, or with Copy-Item / cp). Hash the copy.
  2. Rename the copy to totally-different-name.log, move it into a subfolder, and hash it again.
ItemYour result
Does the copy's hash match the original?
After renaming and moving it?
This is why investigators hash evidence. The name, folder, and timestamps can all change as a file is copied around. The hash recorded when it was collected shows the contents are still exactly the same. You'll see this again in the digital forensics module at the end of the course.

Part 4

Verify a real download

Now do it for real, with a file someone else published.

  1. Pick a vendor that publishes SHA-256 hashes for its downloads. Good choices: the Wireshark installer (its download page links to a signatures file listing SHA-256 values), or any free open-source tool your instructor suggests. Avoid multi-gigabyte files like operating system images unless you have a fast connection.
  2. Download the file from the vendor's own site, and find the published SHA-256 value for that exact file and version.
  3. Hash your download with your platform's command.
  4. Compare the two values. On Linux, if the vendor provides a checksum file, sha256sum -c SHA256SUMS --ignore-missing does the comparison for you.

Verdict
Safety note: you don't need to install anything for this lab. Hash the file, record the result, and delete it if you don't want it. If your hash doesn't match, don't run the file. Download it again from the vendor's site and check again.

Reflection

Write it up

Short answers, in your own words. These aren't auto-graded. This is where you show you understand what the hash proved, not just that you copied it.

1.In Part 2 you changed one character. Why is it useful that the whole hash changed instead of just one character of it?

2.Which of the three security principles (confidentiality, integrity, availability) did this lab test? Could someone who has your notes.txt hash work out what the file says? Why or why not?

3.An attacker takes over a download mirror and replaces both the installer and the hash posted on that mirror's page. Would your Part 4 check catch it? What would?

4.Using Part 3, explain why an investigator records a file's hash at the moment it's collected as evidence.

5.Some vendors still publish MD5 hashes. If MD5 is broken for security, why might a matching MD5 still be worth checking, and what can't it prove?
