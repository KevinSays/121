Evaluating Alerts & Governance and Compliance

A Tier-1 analyst's shift is a queue of alerts, and every one needs an answer: real or not? This session covers where those alerts come from, how to read the rule that fired, and how to classify what you find. Concept 1 · Module 21.1

Sources of Alerts

Alerts come from many detectors, land in one queue, and every one traces back to a rule someone wrote.

Security Onion

Security Onion is an open-source suite of network security monitoring (NSM) tools that runs on Linux. It combines full packet capture, network-based and host-based intrusion detection, and tools for analysts to investigate alerts. It can run as a single standalone system or as separate sensors and a central server.

Detection tools: where alerts are generated

SnortA network IDS (NIDS) that uses rules and signatures to generate alerts. A tool called PulledPork downloads new Snort rules automatically. Both are open source and sponsored by Cisco.
SuricataA signature-based NIDS similar to Snort that can also work inline as an IPS. It uses multithreading to spread work across CPU cores.
ZeekFormerly called Bro. A NIDS that takes a behavior-based approach, using policy scripts to decide what to log and when to alert. It also records detailed HTTP, DNS, and TCP transaction logs.
OSSEC and WazuhHost-based IDS (HIDS): file integrity monitoring, local log monitoring, process monitoring, and rootkit detection. Each host needs an agent. Wazuh is replacing OSSEC in Security Onion.

Analysis tools: where alerts are investigated

SguilThe analyst's console and starting point. It gathers alerts from every source into one timestamped queue, where the analyst can investigate, classify, escalate, or retire each one, and pivot to the other tools.
KibanaAn interactive dashboard over data stored in Elasticsearch, for searching, visualizing, and exploring logs. You can pivot to it from Sguil by IP address.
WiresharkOpens the full packet capture behind an alert, so you can see exactly what was sent.
Zeek logsTransaction records, file content, and other details about the same traffic.

What an alert contains

Alerts generally include the 5-tuple (source IP and port, destination IP and port, and protocol), a timestamp, and which device or sensor generated the alert. Some add whether traffic was permitted or denied, payload data, or file hashes. In Sguil's real-time queue, each row shows:

Sguil columnMeaning
STStatus. RT means real time. Color-coded by priority, from light yellow (very low) to red (high)
CNTCount: how many times this alert has fired for the same source and destination. A very high count may mean a serious problem, or a rule that needs tuning
SensorThe agent that reported the event, such as Snort or OSSEC
Alert IDTwo numbers: the sensor, then the event number
Date/TimeWhen the first of the correlated events happened
Event MessageThe text from the rule that fired. Tick "Show Rule" to see the rule itself

Alerts can be rule-based, signature-based, anomaly-based, or behavior-based, but in every case the conditions that trigger them were defined ahead of time.

Snort rule structure

A Snort rule has two parts: the rule header, which says what traffic to look at, and the rule options, in parentheses, which say what to look for and how to describe it.

PartMeaning
Actionalert generates an alert. Other actions include log and pass
Protocoltcp, udp, icmp, or ip
Source and destinationAddress and port. any matches all. Variables such as $HOME_NET and $EXTERNAL_NET are set in the Snort configuration file. Port ranges use a colon, such as 1:1024
Direction-> means from source to destination
msgThe text shown in the alert
contentText or bytes to match in the packet's payload
referenceA link to more information about the threat
classtypeThe attack category, which sets the alert's priority
sid / revThe rule's unique ID number, and its revision number

Rules come from several sources: GPL (older Sourcefire rules), ET (Emerging Threats, a community collection), and VRT (rules maintained by Cisco Talos, released to subscribers first). Organizations also write custom local rules, conventionally with sid numbers of 1,000,000 and up.

Concept 2 · Module 21.2

Overview of Alert Evaluation

The alert says an exploit happened. Your job is to decide whether that's true.

Why alerts need a human

Attackers constantly change their exploits to get past detection, and no prevention catches everything. So detection rules are written to be conservative: it's better to raise an alert that turns out to be harmless than to miss a real attack. That means a lot of alerts aren't real, and a skilled analyst has to check them. A Tier-1 analyst works the queue in Sguil and pivots to Zeek, Wireshark, and Kibana to confirm or rule out each one.

The four classifications

Every alert, and every attack, lands in one of four boxes, depending on whether an alert fired and whether an attack really happened:

  • True positive: an alert, and a real incident. The rules worked.
  • False positive: an alert, but no real incident. The harmless activity that set it off is a benign trigger. False positives cost analyst time.
  • True negative: no alert, and nothing happened. Normal traffic correctly ignored.
  • False negative: a real incident with no alert. The most dangerous outcome, because the attack goes unnoticed, sometimes for a long time.

What happens next

Suspected true positiveEscalated to a higher tier. Investigators confirm the incident and find what was damaged. Senior staff then contain it, fix the vulnerability, and handle reporting.
Many false positivesReported, because they waste analyst time and bury real alerts. They signal that rules need tuning. A sudden spike often follows a configuration change or newly downloaded rules.
False negativesOften found only later, through retrospective security analysis (RSA): running new rules or new threat intelligence against archived network data. Then the analyst assesses the damage and decides what mitigation is needed.

The four boxes are easy to mix up on a quiz, because the words describe two different things at once. A picture from the castle walls helps keep them apart.

Think of it like… the fire bell in the watchtower In a town of wood and paper, the watchman in the fire tower rings the bell when he sees smoke. Bell, and a house really is burning: true positive, and the fire brigade runs. Bell, but it was a merchant's charcoal brazier: false positive. The brigade wasted a trip, and the brazier is the benign trigger. No bell, no fire: true negative, a quiet night. No bell, but a storehouse is burning behind a wall the watchman can't see: false negative, the one that burns down a ward. A town would rather put up with a few wasted trips than miss a fire. That's why detection rules are written conservatively.

Deterministic and probabilistic analysis

Deterministic analysisJudges risk from what's known about a vulnerability, assuming every step an attacker needs succeeds. It describes the worst case. It relies on known facts, such as an exploit always using a standard, well-known port.
Probabilistic analysisEstimates how likely each next step of an exploit is to succeed, given the previous one did. Used in real time, when many variables are unknown, to predict the most likely paths. Needed for exploits that use dynamic ports, which static rules can miss.

Concept 3 · Module 22.1

Governance

Who is accountable for security decisions, who owns the data, and what the written rules say.

IT security governance

Governance is the oversight that makes sure risks are adequately mitigated. It shows accountability, aligns the security strategy with business goals and regulatory compliance, and decides who in the organization may make cybersecurity risk decisions. Governance doesn't pick individual controls itself. It makes sure someone accountable does, and checks the results. Senior leadership, often through a chief information security officer (CISO), is ultimately accountable.

Data governance roles

Data ownerEnsures data follows policies and procedures, assigns its classification, and decides the criteria for who gets access. Usually a business manager, not IT.
Data custodianImplements the classification and security controls according to the owner's rules: backups, permissions, encryption. Usually IT staff.
Data controllerDecides the purposes for which, and the ways in which, personal data is processed.
Data processorProcesses personal data on the controller's behalf, such as a cloud payroll service.
Data stewardMakes sure data supports the business's needs and meets regulatory requirements.
Data protection officer (DPO)Oversees the organization's overall data protection strategy and compliance.

The owner/custodian split trips people up, because the custodian is the one with hands on the data every day. Think about who decides versus who carries the decision out.

Think of it like… the lord's rice storehouse The rice in the castle storehouse belongs to the lord. The lord, through his chief retainer, decides how precious each store is and who may draw from it. That's the data owner. The storehouse keeper holds the keys, keeps the roof sound, counts the bales, and opens the doors only for those on the approved list. That's the data custodian. The keeper does all the daily work, but doesn't decide who's on the list. If the keeper started handing rice to his friends, he'd be overstepping, however well he guarded the doors.

Cybersecurity policy documents

Governance is written down in a hierarchy of documents, from broad to specific:

DocumentWhat it isExample
PolicyA high-level statement of goals and rules, approved by leadership. Mandatory"All remote access must use multifactor authentication."
StandardSpecific, mandatory requirements that support a policy"Passwords must be at least 14 characters."
ProcedureStep-by-step instructions for carrying out a taskThe steps to onboard a new employee's accounts
GuidelineRecommendations and best practices. Not mandatoryTips for spotting phishing emails

Policies that manage people

Need to knowPeople get access only to the information required for their job. The principle the U.S. government uses in its access control models.
Separation of dutiesA critical task is split between people, so no one person can complete it alone, such as one person approving a payment and another sending it.
Job rotationMoving staff between roles periodically, so no one person holds a role long enough to hide fraud, and so more people know each job.
Mandatory vacationsRequiring people to take time off, so someone else does their work and any irregularities surface.
Acceptable use policy (AUP)Defines what users may and may not do with the organization's systems and network. Enforced with tools such as content filtering.
Security awareness trainingTeaches staff to recognize threats such as phishing, and what the policies require of them.

Technical measures back up the policies: content filtering to enforce the AUP, disabling USB ports and CD drives where they aren't needed, automatic antimalware scans of media, files, and attachments, and write and delete permissions granted only by the data owner.

Concept 4 · Module 22.2

The Ethics of Cybersecurity

Security professionals hold powerful access. Law sets the minimum. Ethics covers the rest.

Why ethics matters here

A security analyst can often read email, see personal files, watch network traffic, and reach systems most employees can't. Professional ethics are the standards of conduct that govern how you use that access. To make informed ethical decisions, a cybersecurity professional needs to understand two things: the laws governing the data they handle, and the organization's legitimate interests. Something can be legal and still be wrong, like browsing a coworker's medical claims out of curiosity because your role happens to allow it.

Liability

PersonalIndividuals are legally responsible for their own actions. "My account had access" isn't a defense for misusing it.
CorporateOrganizations can be held liable, and fined, for failing to protect data or for breaking laws and regulations.
InternationalData and attacks cross borders. An organization may be bound by the laws of every country where it operates or whose residents' data it holds.

Laws and regulations to know

Session 6 introduced HIPAA and PCI DSS and promised a fuller look at compliance. Here it is. Most of these are U.S. federal laws.

Law or standardProtects or covers
HIPAAHealth Insurance Portability and Accountability Act. Patients' health information held by healthcare providers, insurers, and their partners
GLBAGramm-Leach-Bliley Act. Customers' personal financial information at financial institutions. Requires privacy notices and lets people opt out of having their information shared with third parties
SOXSarbanes-Oxley Act. The accuracy of public companies' financial records, and the controls that protect them
FERPAFamily Educational Rights and Privacy Act. Students' education records. Rights pass from parents to the student at 18 or on entering college
PCI DSSPayment Card Industry Data Security Standard. Cardholder data, for anyone who accepts card payments. An industry standard enforced by contract, not a law
CFAAComputer Fraud and Abuse Act (1986). Makes it a crime to knowingly access a computer without authorization, including government computers and those used in interstate commerce
ECPAElectronic Communications Privacy Act. Restricts intercepting electronic communications such as email and phone calls
CIPAChildren's Internet Protection Act. Requires schools and libraries that receive certain federal funding to filter harmful internet content
COPPAChildren's Online Privacy Protection Act. Limits collecting personal information online from children under 13
FISMAFederal Information Security Modernization Act. Information security programs at federal agencies
GDPRThe European Union's General Data Protection Regulation. Personal data of people in the EU, wherever the organization handling it is located

Making an ethical decision

When a situation isn't clear, a few questions help:

  • Is it legal, under every law that applies to this data?
  • Does it follow the organization's policy, and is it within my authorization?
  • Who could be harmed, and how?
  • Would I be comfortable if my manager, the people affected, or the public saw what I did and why?
  • Have I asked someone accountable before acting, rather than deciding alone?

A personal code of ethical conduct

The module asks you to write your own code of conduct. Professional bodies offer models. The ISC2 Code of Ethics, which every ISC2 certification holder agrees to, has four canons:

1Protect society, the common good, necessary public trust and confidence, and the infrastructure.
2Act honorably, honestly, justly, responsibly, and legally.
3Provide diligent and competent service to principals.
4Advance and protect the profession.
Write your own. A useful personal code is short and concrete. For example: "I use my access only for the task I was assigned. I don't look at personal data out of curiosity. I report what I find, including my own mistakes. I don't test or scan anything without written permission. I keep what I learn on the job confidential."

Concept 5 · Module 22.3

IT Security Management Frameworks

Frameworks give organizations a tested structure for choosing controls, and a yardstick for evaluating them.

ISO/IEC 27000 familyInternational standards for an information security management system (ISMS). ISO 27001 sets the requirements for an ISMS, and organizations can be certified against it. ISO 27002 is a catalog of security controls. A statement of applicability (SOA) lists which controls the organization applies and why others don't apply.
CIS Critical Security ControlsFrom the Center for Internet Security. A prioritized set of controls based on the latest information about common cyber attacks, scaled for organizations with different resources and expertise. CIS also publishes configuration benchmarks for specific platforms.
Cloud Security Alliance (CSA)Provides security guidance for any organization using cloud computing, and helps assess a cloud provider's overall security risk. Session 10 covered its domains.
NICE Workforce FrameworkNIST's National Cybersecurity Workforce Framework organizes cybersecurity work into seven categories, so organizations can describe the roles and skills they need.

The seven workforce categories

CategoryWork it covers
Securely ProvisionDesigning and building secure IT systems
Operate and MaintainSupporting and administering systems so they perform securely
Oversee and GovernLeadership, management, and direction of cybersecurity work
Protect and DefendIdentifying, analyzing, and mitigating threats to systems and networks. Where SOC analysts work
AnalyzeHighly specialized review and evaluation of incoming cybersecurity information to determine its usefulness for intelligence
Collect and OperateSpecialized denial and deception operations, and collecting cybersecurity information for intelligence
InvestigateInvestigating cybersecurity events and crimes, including digital forensics

Evaluating the controls

A framework says which controls an organization should have. Checking that they actually work takes testing. Organizations with the resources and expertise run penetration tests and red team exercises, simulated attacks that measure how well the organization's defenses and people hold up. Audits compare actual practice against the chosen framework, and the gaps they find go back to governance to decide what to fix first. Session 15 covers network security testing and risk management in depth.

Classifying alerts

Four from the morning queue

Classify each as a true positive, false positive, true negative, or false negative:

(a) An alert for "SQL injection attempt" against Tsukimi Sweets' shop. The packet capture shows a real injection string, and the database log shows the query ran. (b) An alert for "possible port scan" from a Kaidō Freight address. It's the IT team's scheduled vulnerability scanner. (c) A week later, threat intelligence reveals a new malware family. Searching archived DNS logs shows a Kiriyama workstation contacted its CnC domain days ago, with no alert at the time. (d) A normal login to the hospital portal that raised no alert.

Show answer

(a) True positive: escalate. (b) False positive, with the scanner as the benign trigger. The rule should be tuned to exclude the authorized scanner's address. (c) False negative, found through retrospective security analysis. Investigate the workstation now. (d) True negative.

Reading a rule

What does this rule catch?

alert tcp $HOME_NET any -> $EXTERNAL_NET 21 (msg:"Outbound FTP login"; content:"USER"; sid:1000042; rev:2;)

Explain each part of the header. What traffic triggers it, and what will the analyst see in Sguil?

Show answer

Header: action alert; protocol tcp; source any port on the inside network ($HOME_NET any); direction outbound (->); destination port 21 (FTP) on any outside network.

Triggers: TCP traffic from inside to an outside FTP server whose payload contains USER, the command that sends an FTP username. FTP sends credentials in plaintext, so this catches staff logging into outside FTP servers.

In Sguil: the event message "Outbound FTP login." It's a locally written rule (sid of 1,000,000 or more), now on its second revision.

Tuning

CNT 4,812

Bastion's Sguil queue shows one Kaidō Freight alert with a CNT of 4,812 since a new rule set was downloaded last night. Every event is from the same printer to the same file server. What does the count suggest, and what should the analyst do?

Show answer

A huge count of identical, correlated events that started right after a rule update most likely means a false positive from a rule that doesn't fit this environment. The printer's normal behavior is the benign trigger.

Do: verify a sample with the packet capture to be sure, then report it so the rule can be tuned: adjusted or suppressed for that source. Don't just retire alerts silently. Unreported false positives keep burying real alerts.

Data roles

Who decides who sees the records?

At Kiriyama General Hospital, a new research team asks the database administrator for read access to patient records. The DBA has the technical ability to grant it right away. Who should decide, and what is the DBA's role?

Show answer

The data owner decides: the business leader responsible for patient records, such as the head of health information management. They set the access criteria, under the hospital's policies and HIPAA. The DBA is the data custodian: they carry out the owner's decision and the security controls, but don't make the access decision.

The decision should also follow need to know. The researchers may get a masked or limited data set rather than full records.

Laws

Which rules apply?

Match each Bastion client situation to the law or standard most directly involved: (a) Tsukimi Sweets takes credit cards on its website. (b) Kiriyama General Hospital stores patient diagnoses. (c) A former Kaidō Freight contractor logs in to the company's systems after their contract ended, using an account that was never disabled. (d) Kiriyama runs a small school for nursing students and keeps their grades.

Show answer

(a) PCI DSS, the industry standard for cardholder data. (b) HIPAA. (c) CFAA: knowingly accessing a computer without authorization. Note the governance failure too: offboarding should have disabled the account. (d) FERPA, for student education records.

Ethics

"Just take a quick look"

While investigating a phishing alert, a Bastion analyst has access to a Tsukimi Sweets manager's mailbox. A Tsukimi supervisor, a friend of the analyst, messages: "While you're in there, can you see if they mentioned my raise?" Nothing technical stops the analyst from looking. What should they do, and why?

Show answer

Decline, and limit the mailbox review to what the phishing investigation needs. Run it through the decision questions: it's outside the analyst's authorization and the investigation's scope, so it breaks policy. It may violate privacy law. It harms the manager. And it's not something the analyst could explain to the client.

Access granted for one purpose isn't permission for another. This is exactly the situation a personal code of conduct is for. The analyst should also consider whether the request itself needs to be reported to their lead.
