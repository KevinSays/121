Concept 1 · Module 2.1

The Current Threat Landscape

Before defending a network, it helps to know why it's a target in the first place — and that not every threat comes from outside it.

Networks are targets because of what they connect to: money (financial systems, payment data), identity (personal records), and operations (the systems a business or hospital can't run without). As networks have grown to include cloud services, remote workers, and IoT devices, the attack surface has grown right along with them — more entry points to defend, not just more data to protect.

Internal vs. external threats

TypeWhoWhy it matters
Internal threatAn employee, contractor, or anyone already inside the network's trust boundaryCan be intentional or purely accidental — and often causes more damage than an external attacker because they already have direct physical access to the building and its infrastructure, not just network access
External threatAn attacker with no authorized access at allHas to find a way in first — through a vulnerability, a phish, or an exposed service — before doing anything else

Where data actually walks out the door

VectorExample
Email / messagingSensitive files attached and sent outside the organization, by mistake or on purpose
Unencrypted devicesA stolen or lost laptop/phone with no disk encryption hands over everything on it
Cloud storageA misconfigured, publicly-shared cloud folder or bucket
Removable mediaA USB drive that leaves the building with a copy of a database
Improper access controlSomeone can see data they were never supposed to have access to in the first place
Data loss isn't always an "attack." An unencrypted laptop left in a taxi and a hacker exfiltrating a database cause the same outcome — data in the wrong hands — through very different mechanisms. Both matter to a SOC.

Concept 2 · Module 2.2

Who Is Attacking Our Network?

Session 1 covered threat actors by motivation. This is about how "who's attacking" has changed shape over the decades — and one word that gets used loosely.

Hacker vs. threat actor: "hacker" is historically a neutral term for someone skilled at exploring and manipulating systems — it says nothing about intent. "Threat actor" specifically means someone using that skill to cause harm. Every threat actor could be called a hacker; not every hacker is a threat actor. A vulnerability broker is a specific gray-hat role worth naming: someone who finds exploitable weaknesses and reports or sells them to the affected vendor — sometimes for a reward — rather than exploiting them.

How hacking has evolved

EraWhat defined it
Early daysIndividuals driven by curiosity and bragging rights — exploring systems, early viruses, phone network exploration
Rise of cybercrimeAttacks shift toward money — credit card theft, early malware-for-profit, the first organized groups
TodayProfessionalized, blended, and often state-backed — ransomware-as-a-service, supply-chain compromise, attacks combining social engineering, malware, and protocol abuse in a single campaign
Full motivation-based threat actor breakdown (script kiddie, hacktivist, organized crime, nation-state/APT, insider) is in Session 1, with dossiers on the Bastion Security Threat Board.

Concept 3 · Module 3.1

IP PDU Details

Before you can understand how IP gets attacked, you need to know what's actually in an IP packet's header — and how much IPv6 simplified it.

IPv4 header fieldWhat it does
VersionIdentifies the IP version (4) — always the first thing read
Header Length (IHL)How long the header is — variable, because of the optional Options field
Total LengthSize of the whole packet, header plus data
Identification / Flags / Fragment OffsetUsed to fragment a packet across multiple pieces and reassemble it correctly at the destination — a mechanism some attacks abuse
TTL (Time to Live)Decremented by every router a packet crosses; discarded at zero — prevents packets from looping forever, and is what makes traceroute work
ProtocolTells the destination which upper-layer protocol (TCP, UDP, ICMP) the payload belongs to
Header ChecksumBasic error-check on the header itself, recalculated at every hop
Source / Destination AddressThe addressing everything downstream trusts — and the field IP spoofing forges
OptionsRarely-used optional field, part of why the IPv4 header is variable length
IPv6 drops the excess weight. The IPv6 header is fixed at 40 bytes — no Options field, no header checksum (upper layers already check for errors), and no in-network fragmentation (routers no longer fragment packets; the sending host does, using extension headers instead). Fewer fields for a router to process means faster forwarding, but the security-relevant ones — source/destination address, a TTL equivalent called Hop Limit, and a Next Header field doing the Protocol field's job — all carry over.

Concept 4 · Module 3.2

IP Vulnerabilities & Attacks

IP has no built-in way to verify a source address. Everything in this section exploits that one trust gap.

AttackHow it works
IP spoofingForges the source IP address so traffic — or the blame for it — appears to come from somewhere else
ICMP reconnaissancePing sweeps map which hosts are alive before an attack even starts
ICMP redirectA forged redirect message tricks a host into routing its traffic through an attacker-controlled path
Amplification & reflectionA small spoofed request (e.g. to a DNS or NTP server) triggers a huge response — sent to the victim, not the attacker
Spoofing is the common thread. Once the source address can't be trusted, an attacker can hide behind it, redirect blame to an innocent host, or turn a third-party server into an unwitting weapon.
Dossiers on IP spoofing, ICMP abuse, and TCP SYN flooding are filed in the Bastion Security Attack Log. ARP, DNS, and DHCP attacks get their own dossiers once Module 4 is filed.

Concept 5 · Module 3.3

TCP & UDP Vulnerabilities

TCP's handshake is a feature for reliability and a liability for availability — every half-open connection ties up a resource somewhere.

AttackHow it works
SYN floodOpens thousands of connections and never completes the handshake, until there's no room left for real ones
TCP reset attackA forged RST packet kills a legitimate, already-established connection
TCP session hijackingPredicts or steals sequence numbers to take over a session someone else already authenticated into
UDP floodOverwhelms a target with connectionless UDP traffic — cheap to send, expensive for the target to process

Internal vs. external

Which threat, and why?

Scenario A: a departing employee copies the customer database to a personal USB drive the week before their last day. Scenario B: someone outside the company scans its public IP range looking for open, unpatched services.

Show answer

Scenario A: Internal threat — the employee already had legitimate access; no "break-in" was required.

Scenario B: External threat — the attacker has no access yet and is still looking for a way in.

Evolution of hackers

Then vs. now

In the early days of hacking, a teenager might deface a website purely for bragging rights among peers. Today, a similarly-skilled group runs a ransomware-as-a-service operation complete with a support line for victims paying the ransom.

Show answer

Answer: This is the arc described in "How hacking has evolved" — from individual curiosity and bragging rights toward professionalized, financially-motivated, business-like cybercrime. The skill required didn't necessarily increase; the organization and motive did.

IP PDU

Read the traceroute

A traceroute shows a packet's TTL hitting zero at hop 14, and the router at that hop sends back an ICMP "Time Exceeded" message. Why does this happen, and what is TTL actually protecting against?

Show answer

Answer: Every router that forwards the packet decrements its TTL by 1. When TTL hits 0, the packet is discarded and the router that dropped it reports back. TTL exists to prevent a misrouted or looping packet from circulating the network forever — traceroute exploits this defensive mechanism to map the path itself, sending packets with deliberately low TTLs.

Amplification

Do the math

An attacker sends a 60-byte DNS query with a spoofed source address (the victim's IP). The DNS server responds with a 4,000-byte answer — sent to the victim, who never made the request.

Show answer

Answer: This is an amplification/reflection attack. The amplification factor here is roughly 4000 ÷ 60 ≈ 67× — every byte the attacker sends becomes ~67 bytes hitting the victim, all while the legitimate DNS server does the actual "attacking" without knowing it.

TCP/UDP

Diagnose the logs

A server's connection logs show thousands of sessions stuck in a half-open state — SYN received, but the handshake never completes. Legitimate users can't connect.

Show answer

Answer: SYN flood. The attacker sends SYNs (often with spoofed source addresses) and never sends the final ACK, so every half-open connection sits in the server's connection table until it's full — starving out real traffic.
