Overview

What Session 3 covers

Two modules: first, the everyday network services — ARP, DHCP, DNS on one side, HTTP/email/databases on the other — and how each gets abused, plus the basic mitigations for common attacks in general. Then wireless: how 802.11 actually works, the threats specific to a network with no cable to unplug, and what actually secures one.

  • Explain how ARP, DHCP, and DNS get exploited at the IP-services layer
  • Explain how HTTP, email, and database-backed applications get exploited at the enterprise-services layer
  • Recommend basic mitigations for common attacks, including the four-phase worm response
  • Explain how 802.11 wireless communication works and what's unique about WLAN threats
  • Compare WEP, WPA, WPA2, and WPA3, and Personal vs. Enterprise authentication

Concept 1 · Module 4.1

IP Services Attacks

ARP, DHCP, and DNS all trade identity verification for convenience. This is the section where that trade gets exploited.

AttackHow it works
ARP cache poisoningManipulates ARP caches on the segment so the attacker's MAC address gets mapped to the default gateway's IP address — a classic man-in-the-middle
MAC address spoofingAlters the attacking host's MAC address to match a legitimate one, defeating MAC-based access controls
DHCP starvationFloods a DHCP server with fake DHCPDISCOVER messages until the whole address pool is leased out, denying service to real clients
DHCP spoofingA rogue DHCP server hands out false DNS server addresses, so a client's later visit to a legitimate site gets silently redirected to a fake one
DNS shadowingCompromises a legitimate parent domain, then creates malicious subdomains under it to use in further attacks
DNS cache poisoningInjects falsified information into a resolver's cache, redirecting users from a legitimate site to a malicious one
DNS tunnelingSmuggles data inside DNS queries — a cybersecurity analyst's tell is queries running noticeably longer than average
DNS amplification/reflectionUses open DNS resolvers to multiply a small spoofed request into a much larger flood aimed at the victim, while hiding the true source
Notice the DHCP spoofing detail: the goal usually isn't the gateway itself — it's the DNS server address. Control what DNS server a victim uses, and you control where every domain name they type actually takes them.
Full dossiers on ARP spoofing, DNS cache poisoning, and DHCP spoofing/starvation are filed in the Bastion Security Attack Log, alongside the Module 3 techniques from Session 2.

Concept 2 · Module 4.2

Enterprise Services Attacks

Web applications and email are how most organizations actually do business — and how most organizations actually get breached.

AttackHow it works
HTTP 302 cushioningAbuses HTTP's own redirect response (302) to quietly bounce a victim toward a malicious site instead of the one they requested
SpamBulk unsolicited email flooded to many users — a delivery vector for phishing and malware as much as a nuisance on its own
SQL injectionInjects SQL commands into an insecure input field (often a login form) to manipulate or extract data straight from the backend database
Cross-site scripting (XSS)Injects malicious script into a trusted site's input fields — exploits the same missing input validation SQL injection does, but targets the browser instead of the database
SQL injection and XSS are siblings. Both exist because user input got treated as trusted code instead of untrusted data. One targets what the database executes; the other targets what a victim's browser renders.

Concept 4 · Module 5.1

Wireless Communications

Before wireless threats make sense, the basics: what band, and what's actually different about a medium with no cable to unplug.

BandUsed byTradeoff
2.4 GHz802.11b, 802.11g, and 802.11n (optionally)Longer range, better wall penetration — but crowded by Bluetooth, microwaves, cordless phones, and every neighboring WLAN
5 GHz802.11a, and 802.11n/ac (optionally/typically)Shorter range, less interference, more available bandwidth
The core difference from wired: a wired attacker needs physical access to a cable or a switch port. A wireless attacker just needs to be within range — the "network edge" isn't a wall anymore, it's a signal boundary that leaks into a parking lot.

Concept 5 · Module 5.2

WLAN Threats

Every threat here exploits the fact that radio waves don't check ID before they let you listen.

ThreatHow it works
JammingTransmits noise or another signal on the same frequency to interfere with wireless transmissions — a deliberate DoS
Accidental interferenceNon-malicious devices sharing the same band (microwave ovens, cordless phones) degrade WLAN performance without any attacker involved
Man-in-the-middleOnce a client is on a rogue AP or evil twin, the attacker can read or alter its traffic in real time
War drivingSearching for unsecured wireless networks to exploit, often with a directional antenna to pick up signals from farther away than intended

Concept 6 · Module 5.3

Secure WLANs

Encryption standards got progressively better; some of the "extra" security measures never really worked at all.

StandardNotes
WEPThe original — badly broken, a static shared key that's straightforward to crack. Do not use.
WPAAn improvement over WEP, but still weaker than what followed it
WPA2Based on 802.11i, uses AES encryption — the baseline standard for a long time
WPA3The newest and most secure, with stronger protections than any predecessor

Personal vs. Enterprise authentication

ModeHow it authenticates
Personal (PSK)Every client uses the same pre-shared key — simple to set up, but the key has to be distributed and kept secret, and doesn't change per-user
Enterprise (802.1X)Centralized authentication via a RADIUS server, using EAP — each user authenticates with their own credentials, no shared secret to leak
Two measures that feel like security but mostly aren't: MAC filtering can be defeated by spoofing an allowed client's MAC address — trivial for even an amateur attacker. SSID cloaking just hides the network name from casual view; a determined attacker can still find it. Neither replaces real encryption and authentication.

Worked examples

DHCP

Two DHCP problems, two different attacks

Scenario A: new employees can't get an IP address all morning — the help desk finds the DHCP server's pool is completely empty. Scenario B: employees are getting IP addresses fine, but everyone's browser is quietly landing on a fake login page for sites they know are legitimate.

Show answer

Scenario A: DHCP starvation — the address pool was exhausted by fake DHCPDISCOVER requests, denying real clients a lease.

Scenario B: DHCP spoofing — a rogue DHCP server handed out a malicious DNS server address, redirecting legitimate-looking requests to fake sites.

Enterprise services

Same root cause, two attacks

A company's login page doesn't validate what's typed into its username field. One attacker enters a crafted string that returns the entire user table. Another enters a crafted string that runs a script in the browser of every visitor who views their comment afterward.

Show answer

First attacker: SQL injection — the crafted input was interpreted as a database command.

Second attacker: Cross-site scripting (XSS) — the crafted input was interpreted as executable script by other users' browsers.

Root cause for both: user input was trusted instead of validated.

Worm response

Put the phases in order

A worm is spreading through a company network. The security team isolates the unaffected subnets first, then starts scanning and patching healthy machines while simultaneously tracking down and disconnecting already-infected ones, and finally runs cleanup tools on the machines that got hit.

Show answer

Order: Containment (isolate unaffected subnets) → Inoculation (patch/scan healthy machines, running in parallel with what follows) → Quarantine (disconnect infected machines) → Treatment (disinfect them).

Wireless threats

Rogue AP or evil twin?

Scenario A: IT finds an unauthorized wireless access point plugged into a conference room network jack, put there by an employee who wanted better Wi-Fi in that room. Scenario B: employees' laptops briefly lose connection to "CorpWiFi," then automatically reconnect — but their traffic is now visibly routing through an unfamiliar device.

Show answer

Scenario A: Rogue access point — unauthorized, but not necessarily malicious in origin here (a well-meaning employee, not an attacker).

Scenario B: Evil twin — the disconnect/reconnect pattern is the signature of a jamming or disassociation attack forcing clients onto an attacker's AP broadcasting the same SSID.

Secure WLANs

Personal or Enterprise?

A coffee shop gives every customer the same Wi-Fi password printed on a receipt. A hospital instead requires every staff member to log in with their own individual network username and password before their device gets wireless access.

Show answer

Coffee shop: Personal (PSK) — one shared key for everyone, simple to distribute, appropriate for low-stakes public access.

Hospital: Enterprise (802.1X) — individual credentials authenticated against a RADIUS server, appropriate where accountability and stronger security matter.
